สเปก: Sync Category + Sub-Category จาก QA Sheet ลง Dashboard

โปรเจกต์: BBL Migration Parity Checker  ·  วันที่: 6 สิงหาคม 2026  ·  สถานะ: รอ review  ·  Branch: feat/criteria-v2

สรุปย่อ

Filter category + sub-category บน dashboard มีอยู่แล้วและทำงานถูกต้อง — ที่ขาดคือข้อมูล เพราะตอน fetch รอบก่อน คอลัมน์ Category / Sub-Category ใน sheet ยังว่าง ตอนนี้ QA กรอกแล้ว งานนี้จึงเป็นแค่การพาข้อมูลจาก sheet ลงมาถึง dashboard = เพิ่มสคริปต์ใหม่ 1 ไฟล์ ไม่แก้ไฟล์เดิมสักไฟล์

1. ทำไมต้องมีสคริปต์ใหม่ ทั้งที่ pipeline มีอยู่แล้ว

เส้นทางข้อมูลปกติคือ sheet → CSV → results.json → dashboard ตอนนี้ขาดช่วงกลาง:

  sheet (มี category แล้ว ✓)
     │  npm run fetch:priority
     ▼
  data/urls-priority.csv  ─────────────  category ว่างทั้ง 88 แถว  ✗
     │  ???  ← ช่วงที่ขาด
     ▼
  data/results-priority.json  ─────────  category ว่างทั้ง 65 หน้า  ✗
     │  npm run dashboard
     ▼
  dashboard  ──────────────────────────  dropdown โล่ง

ขั้น fetch แก้ได้เองแค่รันใหม่ (column mapping ใน fetch-priority-urls.js ถูกอยู่แล้ว — row[3]=Category, row[4]=Sub-Category) แต่ขั้นถัดไปไม่มีทางลัด:

วิธีที่มีอยู่ทำไมใช้ไม่ได้
compare.js (ไม่ --force) มัน sync category จาก CSV ให้อยู่แล้ว (บรรทัด 779–781) แต่เฉพาะหน้าที่มันวิ่งผ่าน — และมันจะพยายาม capture 23 หน้าที่ยังไม่เคยเก็บ เสี่ยง WAF
rescore.js อ่านแค่ results JSON ไม่รู้จัก CSV เลย — ไม่มี category ให้ sync

จึงต้องมีสคริปต์เล็กๆ ที่ทำหน้าที่ตรงนี้อย่างเดียว: อ่าน CSV แล้วแปะ 2 ฟิลด์ลง results JSON ไม่เปิด browser ไม่แตะ network

2. สคริปต์: src/sync-meta.js

node src/sync-meta.js --urls=data/urls-priority.csv \
                      --source=data/results-priority.json [--dry-run]

ทำอะไร

  • อ่าน CSV → map id → { category, subCategory } (id = ตำแหน่งแถว ตรงกับที่ compare.js ใช้)
  • แปะลงแต่ละหน้าใน results JSON แบบสร้าง object ใหม่ { ...page, category, subCategory }
  • เขียนไฟล์กลับ พร้อม backup ก่อนแบบเดียวกับ rescore.js

ไม่แตะอะไร

prodUrl, aemUrl, prod, aem, parity, checks, gaps, screenshot paths — คะแนนทุกหน้าคงเดิมเป๊ะ ไม่ต้องรัน rescore.js ตาม

กติกาการแปลงค่า — มีข้อเดียว

subCategory ที่เป็น "-" (41 แถว) แปลว่า "ไม่มี sub-category" ไม่ใช่ชื่อหมวด → แปลงเป็นค่าว่าง มิฉะนั้น dropdown จะมีตัวเลือกชื่อ - โผล่มา
หน้าเหล่านี้ยังหาเจอผ่าน filter category ได้ตามปกติ

นอกจากนี้ sync ตามที่ sheet เขียนมาทุกอย่าง — รวมถึง "Save andI nvest" (5 แถว) ที่พิมพ์ผิดจาก "Save and Invest" (6 แถว) จะโผล่เป็น 2 ตัวเลือกใน dropdown ตามข้อมูลจริง ถือเป็นสัญญาณให้ทีม QA ไปแก้ที่ sheet ต้นทาง

Guard: ตรวจ id drift ก่อนเขียน สำคัญ

จับคู่ด้วย id แล้ว verify ว่า prodUrl ตรงกัน ถ้าไม่ตรง = abort ไม่เขียนอะไรเลย

if (row.prodUrl !== page.prodUrl) drift.push({ id: page.id, ... });
...
if (drift.length) {
  console.error(`❌ id drift — ${drift.length} page(s) mismatch. NOTHING written.`);
  process.exit(1);
}

ทำไมต้องมี: เคสจริงที่บันทึกไว้ใน fetch-priority-urls.js — วันที่ 5 ส.ค. 2026 มีการแทรกแถว "Web-Forms" ใกล้ต้น sheet ทำให้ id 9–15 เลื่อน และคะแนนของ About-Us เกือบไปผูกกับ Web-Forms

สคริปต์นี้แตะทุกหน้าพร้อมกัน ถ้า id เลื่อนแล้วเขียนเงียบๆ จะได้ category ผิดยกชุดโดยไม่มีใครรู้ — 3 บรรทัดนี้ทำให้มันเป็น drift detector ไปในตัว

📦 backed up → data/results-priority.json.backup-2026-08-06T...

คุณสมบัติ

  • Idempotent — รันซ้ำได้ ผลเหมือนเดิม
  • --dry-run — พิมพ์สรุปอย่างเดียว ไม่เขียนไฟล์ (ตามธรรมเนียม sync-sheet.js)
  • ใช้ได้กับทุก pipeline — ไม่ผูกกับ priority เพราะรับ path ทาง flag

3. ลำดับการรัน

  npm run fetch:priority
        │   sheet → CSV พร้อม category (แถวเดิมคง id เดิม แถวใหม่ต่อท้าย)
        │   ทำได้ทันที ไม่ต้องรอ loop
        ▼
  ⏳ รอให้ chunk ที่กำลังวิ่งจบ (~1-2 นาที) — ไม่ต้องรอ loop ทั้งหมด
        │   เช็คด้วย: pgrep -f "compare.js"
        ▼
  node src/sync-meta.js --urls=data/urls-priority.csv \
                        --source=data/results-priority.json --dry-run
  node src/sync-meta.js --urls=data/urls-priority.csv \
                        --source=data/results-priority.json
        │
        ▼
  node src/build-dashboard.js --source=data/results-priority.json \
                              --prefix=priority --criteria=v2
        │   ← category ขึ้น dashboard ตั้งแต่ตอนนี้ สำหรับหน้าที่ capture แล้ว
        ▼
  loop วิ่งต่อในพื้นหลัง — หน้าที่เก็บเพิ่มได้ category จาก CSV เอง
  ไม่ต้อง sync ซ้ำ (แต่รันซ้ำได้ ไม่มีผลเสีย)

ข้อควรระวัง 1 — sync ได้ระหว่าง cooldown แต่ห้ามชน chunk ที่กำลังวิ่ง

compare.js โหลดไฟล์ results ตอนเริ่ม process (บรรทัด 1022) แล้ว mergePreserved เก็บหน้านอก chunk ไว้ verbatim จากสำเนานั้น และ capture loop spawn process ใหม่ทุก chunk → หน้าต่างที่ sync แล้วโดนทับมีแค่ ~1–2 นาทีที่ chunk กำลังวิ่ง ไม่ใช่ตลอด cooldown 45–75 นาที

ยิ่งกว่านั้น processPair กระจาย ...pair ซึ่งพก category จาก CSV มาด้วย ดังนั้นเมื่อ CSV มี category แล้ว compare.js จะเขียน category ให้เองสำหรับหน้าที่มันเก็บ — ค่าที่ได้ตรงกับ sync-meta.js เพราะอ่าน CSV ตัวเดียวกัน

วิธีปฏิบัติ: ก่อน sync ให้เช็คว่าไม่มี compare.js วิ่งอยู่ แล้วค่อยรัน — ไม่ต้องรอ loop จบทั้งหมด

pgrep -f "compare.js" && echo "chunk กำลังวิ่ง — รอสักครู่" || node src/sync-meta.js …

ข้อควรระวัง 2 — re-fetch จะทำให้ capture loop ยาวขึ้น ~10 ชม.

sheet มี 101 แถว vs CSV 88 → fetch จะเพิ่มราว 13 แถวเป็น id 89+

remaining() ใน capture loop อ่านจำนวนแถวรวมจาก CSV ใหม่ทุกรอบ (total = อ่าน urls-priority.csv ... .length - 1) ไม่ได้ snapshot ไว้ตอนเริ่ม ดังนั้นแถวใหม่จะเข้าคิว fresh อัตโนมัติทันทีที่ CSV โต — ไม่ต้องสั่ง capture รอบใหม่แยก แต่ loop จะยาวขึ้นราว 13 หน้า ≈ 10 ชั่วโมง ตามจังหวะ cooldown

ผลข้างเคียงที่ต้องรู้: การ sync category จะต้องเลื่อนไปรอ loop ที่ยาวขึ้นนี้จบด้วย ถ้าอยากได้ category บน dashboard เร็วกว่านั้น ให้ re-fetch หลัง loop ปัจจุบันจบแทน
